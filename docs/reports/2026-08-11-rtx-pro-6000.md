# RTX PRO 6000 native benchmark — 2026-08-11

This report records the retained native Burn baseline, the historical portable-WGPU optimization,
the accepted forced-blackbox native-WGPU path (including the 2026-08-12 1K optimization addendum),
and matching pinned upstream references. The
256x256 rows accompany the fixture-backed Turbo/1K Edit numerical gates. The 1024x1024 rows are
released-shape operational and performance evidence; they are not 1024x1024 injected-tensor parity,
and no browser result is implied. The later Edit-Turbo 1.5K runtime is recorded below as an
artifact-validated, numerically accepted extension with a measured performance gap.

### GPU utilization during accepted 1K runs

The benchmark harness sampled PID framebuffer residency and board-level NVIDIA telemetry at about
4 Hz. For rows where the Burn PID held framebuffer memory and board GPU utilization was at least
90%, Turbo had 103 samples with mean GPU/memory-controller utilization `99.82%/10.19%`, mean power
`338.03 W`, peak power `453.29 W`, PID framebuffer peak `44,129 MiB`, and board framebuffer peak
`45,724 MiB`. Edit had 109 such samples at `99.81%/9.88%`, mean/peak power
`349.98/450.89 W`, PID peak `46,045 MiB`, and board peak `47,580 MiB`.

This demonstrates compute-busy GPU intervals and large device residency, but it is not a direct
kernel-occupancy trace. GPU utilization and power are board aggregates, so the desktop or remote
rendering process can contribute. The much lower memory-controller percentage is consistent with
the DMD stage being compute/dispatch bound; it does not indicate a CPU inference fallback.

The final runtime additionally overlaps exact host-noise generation with uncached GPU
conditioning and converts F16 decoder output directly to RGB8 without allocating a full F32 host
image. Its Turbo PNG remains byte-identical. A post-change replay occurred while unrelated desktop
work already consumed `10-25%` board GPU utilization with no model PID. The model still averaged
`99.67%` utilization over 110 hot samples, but mean/peak power fell to `322.21/409.68 W` and
contended p50/p95 was `4.019487101/4.045008616 s`; a no-sampler confirmation was
`4.034059261/4.055311088 s`. These runs are retained as contention evidence rather than replacing
the accepted comparison. A same-session composed-Q/K control measured
`4.098237399/4.106558598 s`, so balanced Q/K remained about `64 ms` faster at p50.

The separate 1.5K q128/q16384/VAE-q4096 `p4/kv1/q1` repeat-three profile contained 37 board samples
at or above 90% GPU utilization, averaging `99.89%` GPU and `11.27%` memory-controller utilization
at `359.51 W`, with `424 W` peak power and a `46,041 MiB` Boogu PID framebuffer peak. Its output
hash matches the accepted 1.5K baseline. Because that trace predates report fields explicitly
naming deferred synchronization and composed Q/K preparation, it is utilization/residency evidence
for the 1.5K runtime, not a replacement exact-policy timing or parity report.

## Edit-Turbo 1.5K extension status

`edit-turbo-1k5` is a separate native release identity sourced from the official 1.5K hotfix at
`60981c49e48cffadf2c169532a4ba3f6108afd5e`. Its omitted-size default is 1536x1536; the native
frontend exposes the official aspect-ratio presets within a 2368-side and 2,360,832-pixel envelope.
It cannot load a 1K Edit manifest, and the browser factory rejects it before artifact loading.

The mixed-F16 bundle is sealed as
`4e8b12ac5ca95272f9009080a23baf1bc52d1b0e7aebf2e9e5f394a492369213`. Strict verification covered
249 files totaling 38,224,723,721 bytes, 223 bounded objects, and 1,940 tensors. The verifier report
SHA-256 is `b702ef29e4a9e26afc67d2fdf8ad46582f561995d6041763439a6ed7ef3ee64f`.

An external 372-tensor BF16 1536x1536 schema-2 release fixture includes exhaustive Qwen and
denoiser hook capture. Its upstream F16-versus-BF16 execution floor is Qwen relative RMSE/cosine
`0.08991885/0.9959498`, worst step-3 velocity `0.12197143/0.9925767`, final latent
`0.07775216/0.9969973`, decode `0.07990684/0.9969029`, and final RGB `34.0048 dB/0.9916225` SSIM.
Those values calibrate expected upstream dtype drift; they are not Burn parity measurements.

The fresh-process gate took `131.883 s`, including verified load and cold compilation/autotune, so
it is numerical evidence rather than a performance sample. The separate synchronized performance
comparison used the same prompt/source/seed, uncached conditioning, and five warm samples in each
runtime. The table uses nearest-rank p95 for both sample sets; the upstream JSON's linearly
interpolated p95 is `6.002870 s`. Burn's exact released policy was retained Qwen q128 with
synchronization deferred to its terminal stage barrier, `p4/kv1/q1`
denoiser q16384 with strict-F32 RMSNorm and composed Q/K preparation, and VAE q4096. Its p50/p95
miss the two-times budgets by `0.616/0.823 s`, so
performance parity is not achieved. The target remains `<= 2x`; 1K Edit rows are not proxies.
Qwen q128 passes all 70 captured stages and the portable denoiser passes all 240 captured
boundaries; accelerated attention is gated through propagated full-chain boundaries. Browser
WebGPU remains unsupported for this variant.

The five-warm Burn stage p50 values were processing `2.136 ms`, Qwen `181.861 ms`, Edit VAE encode
`11.052 ms`, four-step DMD `11,702.996 ms`, VAE decode `580.527 ms`, and output `42.264 ms`. The
output was independently decoded as a 1536x1536 RGB PNG.

Deferred Qwen synchronization also passed the complete fixture chain. It must not be described as
byte-identical to per-stage synchronization: a separate standard-RNG output comparison measured
pixel RMSE `1.2151/255`, PSNR `46.4385 dB`, SSIM approximately `0.997171`, and maximum channel
difference `65`. Its repeat-six diagnostic measured `12.535297/13.006941 s` p50/p95; a first-warm
compilation outlier makes that nearest-rank p95 unsuitable as a replacement baseline. Deferred
synchronization is accepted within the numerical gates, not as an exact-PNG claim or a route to the
still-unmet 1.5K `<= 2x` target.

The last safe blackbox alternative, `p2/kv2/q1` at the same q16384/VAE-q2048 bounds, regressed to
p50/p95 `15.768605/15.905656 s` (`2.6418x/2.6492x`) and was rejected. Its JSON SHA-256 is
`38eb72c120d4a9a18a6dc7e626e70eecaf1f41a9c0eae79e920a7a2bd2780dcb`.
The stock 8-plane attention hardware diagnostic failed with maximum error `1.3017578`, RMSE
`0.824376`, and cosine `NaN`. An isolated CubeK shared-workspace repair subsequently passed the
propagated full-chain gate, but regressed to `12.940407/13.052121 s` p50/p95. Because it was slower
and a workspace root patch would not propagate to package consumers, the override was removed and
p8 remains outside the shipped configuration.

Host RoPE lookup precomputation is retained because its 1.5K construction is bit-exact against the
scalar implementation and the exact full chain passes (report SHA-256
`9484d2a87182c3357fe4ef988730892a643435757078c2e2091619501d30e2ff`). At the 1.5K geometry it
reduces host transcendental evaluations from roughly `13.38 million` to `71.1 thousand` unique
lookups (`~188x`). The safe single-query-chunk attention path also skips an unnecessary
concatenate.

Several numerically safe candidates were rejected on clean performance: a persistent device RoPE
cache regressed to `13.8453/14.2948 s`; full fused Q/K RMSNorm+RoPE+GQA passed parity but measured
`13.6063 s` p50; narrow fused RoPE/GQA padding failed to beat the clean production baseline;
balanced Q/K preparation measured `13.6188 s` p50 at 1.5K; and splitting the double-stream shared
projection was neutral at `13.6226 s` p50 with balanced Q/K. These paths remain default-off or were
reverted; 1.5K continues to use its separately qualified composed Q/K policy.
